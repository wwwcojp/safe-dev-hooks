# quality_gate

## 目的

`Edit`/`Write` で編集されたファイルに対しlint/formatチェックを実行し、失敗した場合はClaudeへフィードバックして自己修正させる(または警告のみに留める)。

## 対象イベント / matcher

- イベント: `PostToolUse`
- matcher: `Edit|Write`
- timeout: 90秒(`hooks/hooks.json`。個別コマンドの内部タイムアウトは45秒)

編集先ファイルが存在しない場合(削除された等)は何もしない。

## 判定基準

`.claude-hooks.json` の `quality_gate.commands` に、編集ファイル名(`fnmatch` によるファイル名一致。ディレクトリを含むパスパターンでは一致しない)に対応するコマンド配列が定義されていればそれを使用する。未定義の場合は自動検出にフォールバックする。

### 自動検出(`commands` 未指定時)

| 対象拡張子 | 必要な実行ファイル | 前提設定ファイル(いずれか) | 実行コマンド |
|---|---|---|---|
| `*.py` | `ruff` | `pyproject.toml` / `ruff.toml` / `.ruff.toml` | `ruff check {file}` |
| `*.rs` | `rustfmt` | `Cargo.toml` | `rustfmt --check {file}` |
| `*.js` / `*.jsx` / `*.ts` / `*.tsx` | `npx` | `package.json` | `npx --no-install eslint {file}` |

実行ファイルが `PATH` に無い、または前提設定ファイルがプロジェクトルート直下に無い場合はそのコマンドをスキップする。いずれの条件も満たさなければ何もしない。「プロジェクトルート」は `hooks/lib/config.py` の `project_root(cwd)`(`CLAUDE_PROJECT_DIR` → cwdの最近傍のgitルート → cwd)で決定する([docs/configuration.md](../configuration.md) 参照)。

**自動検出は承認済みプロジェクトでのみ実行する(0.8.0)**: `ruff`/`rustfmt`/`npx eslint` はいずれもプロジェクト同梱の設定ファイルを読み込み、`eslint.config.js` に至っては JavaScript として評価される。これをリポジトリの承認前に実行するのは、`.claude-hooks.json` の未承認内容をマージしないという 0.7.0 の原則に反する。そこで自動検出は、グローバル設定 `$HOME/.claude/claude-hooks.json` の `trusted_projects` にそのプロジェクトのエントリがある場合(内容ピン留め `"sha256:…"` またはピン留めなし `true`。`false` と未登録は非承認)に限り実行する。承認の有無は判定していない `.claude-hooks.json` の**有無とは無関係**であり、判定しているのは「利用者がこのディレクトリ(プロジェクトルート)を承認したか」である(設定ファイルが無いプロジェクトでも、承認さえされていれば自動検出は動く)。ピン留め承認(`"sha256:…"`)は、ハッシュが現在の `.claude-hooks.json` の内容と**一致しない場合でも**、自動検出の可否としては承認済みとして扱う(その設定ファイル自体は不採用になり、変更検知の警告が出る)。ピンが担保するのは`.claude-hooks.json` の内容であって、自動検出が実際に読む設定ファイル(`eslint.config.js`・`ruff.toml`・`pyproject.toml`)ではないためで、ハッシュ一致を条件にしても実際の脅威は減らず、`.claude-hooks.json` を直すたびに lint が止まって利用者をピン留めなし承認(`true`)へ誘導するだけになる。利用者が `quality_gate.commands` に明示したコマンドはこの制限を受けない — グローバル設定に書いたものはもともと承認不要、プロジェクト設定に書いたものは 0.7.0 のプロジェクト設定ゲート自体で既に承認制になっている。

**承認は編集対象ファイルが root の実境界内にあることも要求する(0.8.0)**: 承認は cwd 側のプロジェクトルート(`root`)に対するものであり、「`root` が承認済みなら自動検出する」だけでは、承認済み `root` を足場に `root` 外の未承認ファイルを `file_path` に指定する経路(ESLint 等は lint 対象ファイルの場所から設定を探索するため、cwd 側の承認は file_path 側の未承認 `eslint.config.js` を読ませない保証にならない)と、`CLAUDE_PROJECT_DIR` で承認済みの祖先へ `root` を持ち上げ、自前の `.git` を持つ未承認のネストしたクローン(vendored clone 等)を巻き込む経路の2つが自動検出に到達できてしまう。そこで `hooks/post_tool_use/quality_gate.py` の `_in_trusted_scope` が、file_path が (a) `root` 配下(realpath 同士のパス包含)であり、かつ (b) `file_path` から `root` へ遡る途中に(`root` 自身を除き)別の `.git` 境界が無いことの両方を要求する。どちらか一方でも欠ければ自動検出しない。

**未承認スキップの通知は副作用なしの事前判定に基づく(0.8.0)**: 通知条件は「未承認 かつ コマンド未解決」ではなく、`would_autodetect`(拡張子一致・前提設定ファイルの有無・実行ファイルの `PATH` 上の有無・上記の境界判定のみを見て、プロセスは一切起動しない)が真になる場合、すなわち「承認していれば実際に自動検出コマンドが生成されたはずの場合」に限る。マーカーファイルが無い、対象拡張子でない、実行ファイルが `PATH` に無い、または境界外である場合は、承認しても何も変わらないため通知しない(例: マーカー無しのプロジェクトで `README.md` を編集しても通知は出ない)。`trusted_projects` に `false`(明示的な不承認)で登録されているプロジェクトにも通知しない — 利用者はすでに承認しないと答えており、0.7.0 のプロジェクト設定ゲートが `false` で沈黙するのと同じ規約である。未承認のため自動検出をスキップして通知した場合は `systemMessage` に印字する(既定 1 時間のクールダウン、`notice_cooldown_sec` で調整)。そのプロジェクトに `.claude-hooks.json` がある場合、この通知は貼り付け用の承認エントリを**出さない** — 同じキーに対する承認エントリは `.claude-hooks.json` の未承認通知が内容ハッシュ形式(`"sha256:…"`)で示しており、両方を並べると同一キーに 2 つの異なる値が並んでしまう(しかも先に目に入るのが弱い `true` になる)。設定ファイルが無いプロジェクトではピン留めする内容が存在しないため、従来どおり `true` のエントリを示す。詳細: [docs/security-model.md](../security-model.md) §2、既知の限界は下記および同 §4。

**承認キーと自動検出の起点は同じ値(0.8.0)**: 基準ディレクトリ(`root`)は `hooks/lib/config.py` の `load_config` が承認判定に使った値をそのまま `_project_root` として公開し、`quality_gate` は再計算せずそれを使う。1 イベントにつき `project_root` の解決は 1 回だけであり、「どのディレクトリが承認されたか」と「どのディレクトリを起点に自動検出するか」が構造的に一致する。(イベントに `cwd` が無い場合、両者を独立に導出すると承認済みプロジェクトの名義で未承認クローンのファイルを lint できてしまう経路があった。)

**実行ディレクトリ(0.7.1)**: `commands` で明示設定したコマンドも自動検出コマンドも、区別なく**プロジェクトルートを実行ディレクトリ**として実行する。`{file}` は Edit/Write が常に絶対パスで渡すため置換結果はこの変更の影響を受けないが、利用者が `commands` に書いた**相対パスを含む独自コマンド**は、従来の `cwd`(作業ディレクトリ)ではなく**プロジェクトルート**基準で解決されるようになった点に注意。

### block になる条件

コマンドが1つ以上実行され、いずれかが非ゼロ終了した場合。`quality_gate.mode` が `"block"`(既定)であれば `decision: "block"` を返し、失敗したコマンドと出力の末尾1500文字をClaudeへ提示して修正を促す。

### warnになる条件

同じ失敗条件で `quality_gate.mode` が `"warn"` の場合、`additionalContext` に警告文を追加するのみでツール実行は継続する。

### 何もしない条件

対象コマンドが無い、または全コマンドが成功した場合。

## 設定キー

| キー | 既定値 | 説明 |
|---|---|---|
| `quality_gate.enabled` | `true` | falseで本Hookを無効化 |
| `quality_gate.mode` | `"block"` | `"block"` = Claudeに修正させる / `"warn"` = 注記のみ |
| `quality_gate.commands` | `{}` | `{"<ファイル名glob>": ["コマンド {file} ..."]}`。`{file}` は `shlex.quote` 済みのファイルパスに置換される。指定するとそのglobに対する自動検出は使われない |

## 既知の限界

- `commands` のキーは `fnmatch` による**ファイル名のみ**の一致であり、ディレクトリを含むパスパターン(例: `"src/*.py"`)は一致しない。
- 自動検出はプロジェクト**ルート直下**の設定ファイル(`pyproject.toml` 等)の有無のみで判定するため、モノレポでサブディレクトリにのみ設定ファイルがある場合は自動検出されない。
- `npx --no-install eslint` はローカルインストール済みのESLintのみを使う(グローバルインストールへのフォールバックはしない)ため、ローカル未導入のプロジェクトでは自動検出コマンドが実行できず失敗として記録される(`エラーコード != 0` として `run_checks` に失敗扱いで積まれる)。
- 1本のコマンドにつき内部タイムアウトは45秒。複数コマンドが直列実行されるため、Hook全体のtimeout(90秒)を超えると強制終了され得る。
- 対象は編集された1ファイルのみで、プロジェクト全体のlintは実行しない。
- Hook自体の異常時は fail-open(検査スキップ、編集は通過)。
- **境界判定は `.git` の有無を使うため、承認済みプロジェクト内の、`.git` がファイルである入れ子リポジトリ(git submodule・linked worktree)は自動検出の対象外になり、通知も出ない(0.8.0)**。submodule の `.git` はディレクトリでなくファイルで、`git worktree add` で作る linked worktree の `.git` も同様にファイルであるため、いずれも同じ境界として扱われる(実測でも同一の無言スキップを確認)。これらの内側のファイル編集は「承認していれば動いたはず」の判定自体が偽になるため、承認を促す通知が無言で出ない。fail-safe 側の挙動であり「これらは利用者が承認していない別リポジトリ」という解釈とも整合するが、無言である点に注意。詳細: [docs/security-model.md](../security-model.md) §4。
- **`.git` を持たない未承認の vendored サブツリーは、依然として自動検出の対象になる(0.8.0、既知の限界)**。`.git` 境界のヒューリスティックは部分的な防御に過ぎない。詳細: [docs/security-model.md](../security-model.md) §4。
- root 内のシンボリックリンク/ハードリンクが root 外のファイルを指す場合、その**内容**は lint 対象になり得る(0.8.0)。ただし設定探索(前提設定ファイルの場所)は root 内に留まるため、未承認の設定が評価される脅威にはならない。詳細: [docs/security-model.md](../security-model.md) §4。
