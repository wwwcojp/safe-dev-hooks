# プロジェクト設定のオプトイン信頼(`.claude-hooks.json` 信頼層分離)設計

- 日付: 2026-07-26
- 対象バージョン: 0.7.0
- ステータス: ドラフト(第3版 — ピン留めなし承認を追加)

## 背景と目的

セキュリティスキャン(2026-07-25、リビジョン `ff34449`、検証パネル通過 12 件)で、**12 件すべてが単一の根本原因に収束**した。`hooks/lib/config.py` の `load_config` が、開いているリポジトリに同梱される `.claude-hooks.json` を、ユーザー自身のグローバル設定と信頼レベルの区別なく**最高優先度でマージ**していることである。

この設定層は 2 種類のシンクへ到達する。

1. **deny 判定の緩和** — `secrets_guard.allow_paths`、`bash_guard.allow`、`exfil_guard.trusted_servers`、`exfil_guard.categories.*: "off"`、`bash_guard.protected_branches: []`
2. **コマンド実行** — `quality_gate.commands`、`notify.command`、`scanners.gitleaks_image` / `gitleaks_config`(`docker run` するイメージと任意ホストパスの bind-mount)

いずれも敵対的リポジトリを `git clone` して開くだけで成立する。プラグイン自身の write_protected は無関係である — ファイルは Edit/Write ではなく git 経由で到着するためである。これは `docs/security-model.md` §2(「設定ファイルからの deny 層解除不可」)と `docs/configuration.md` §3(「deny の解除は不可」)が明示的に保証している性質に反する。**約束が実装を上回っている状態**であり、本 spec はその差を実装側で埋める。

### 却下された先行アプローチ(重要)

同スキャンの修正フェーズで、**危険な鍵を列挙して拒否する denylist 方式**を 2 ラウンド試作し、独立検証で 2 回とも却下された。却下理由はいずれも**列挙の漏れ**である。

| ラウンド | 見落とし | 種類 |
|---|---|---|
| 1 | セクション単位の型すり替え(`{"exfil_guard": 0}` が型検証フォールバックを誘発し、**グローバル**の強化値を既定値へ戻す) | 形状 |
| 2 | `custom_patterns` の**要素**が未検証(`[{}]` で消費側が例外 → fail-open でガード停止) | 深さ・要素内容 |

denylist は鍵・形状・深さ・要素内容の 4 軸すべてを網羅する必要があり、`DEFAULTS` に鍵を追加するたびに同期漏れが穴になる。`.claude/rules/guard-rule-changes.md` 原則3(「列挙でなく境界アンカーで」)と同じ失敗クラスが設定層で再発した形である。allowlist への反転も列挙の向きが変わるだけで、維持すべき表は残る。

**本 spec は列挙そのものを廃止する。** デフォルトでプロジェクト層を一切採用せず、ユーザーの明示的な承認によってのみ採用する(オプトイン)。承認済みなら全権限を与える。これにより同期すべき鍵の表が存在しなくなる。

前例: VS Code Workspace Trust、direnv の `direnv allow`、git の `safe.directory`。

### 第2版で追加された論点(設計レビュー指摘)

第1版に対する独立レビューで blocking 3 件が指摘され、いずれも実コードで再現を確認した。第2版はこれらを反映している。

1. **信頼ゲート自身が Round 1 の失敗を再現する** — 承認判定は既存の型検証より前に走るため、グローバル設定の `trusted_projects` が不正な型(`[]`・`null` 等、悪意でなく打ち間違いで十分)だと添字アクセスが `TypeError` を投げ、F3 で導入した外側の `except Exception` が**全設定を DEFAULTS へ落とす**。→ 挙動仕様 #1・#2 で明示的に対処する。
2. **型検証のフォールバック先がビルトイン `DEFAULTS` であり、直下の層ではない** — 現行コード(`hooks/lib/config.py:98-101`)の実測で、グローバルに `mode: "always"` / `categories.pii: "deny"` を設定した状態にプロジェクトから `{"exfil_guard": 0}` を与えると `detect` / `ask` へ戻る。**これは本 spec 以前から HEAD に存在する実バグ**であり、承認済みプロジェクトに対しては本 spec 後も残る。→ 挙動仕様 #5 として本 spec に取り込む。
3. **通知の配線先と流量が未指定** — `load_config` は 9 フックから独立に呼ばれ、`Edit` 1 回で 5 回呼ばれる。配線機構を指定しなければ、廃止したはずの「列挙の同期漏れ」が鍵の表から 9 ファイルの通知実装へ移るだけになる。→ 挙動仕様 #3 で一元化と流量制御を規定する。

## 決定事項

| 論点 | 決定 |
|---|---|
| 信頼層 | **信頼**: ビルトイン `DEFAULTS` + グローバル `$HOME/.claude/claude-hooks.json`。**非信頼**: `<cwd>/.claude-hooks.json` |
| 既定の挙動 | 非信頼層は**マージしない**。承認済みのときのみマージする |
| 承認の粒度 | **プロジェクト単位のみ**。セクション別・鍵別の部分承認は作らない(allowlist の再導入になり、列挙が戻るため) |
| 承認済みの権限 | **全権限**(現行と同一の最高優先度マージ)。承認行為そのものがセキュリティ判断である |
| 承認記録の置き場所 | グローバル設定の新規トップレベルキー `trusted_projects`。**リポジトリ外**に置くことが必須(リポジトリ内なら攻撃者が自分で書ける) |
| 承認の固定方法(既定) | **プロジェクト設定ファイルの内容ハッシュで固定**(direnv 方式)。通知が印字する承認エントリは常にこの形式であり、貼り付けるだけの経路は必ず安全側になる |
| ピン留めなし承認 | 人間が**明示的にオプトイン**する場合に限り、内容ハッシュを問わない承認を認める(値に真偽値 `true` を書く)。頻繁に設定を編集するリポジトリでの再承認の摩擦を避けるため。既定ではない |
| ピン留めなし時の検出 | ピン留めなしでも**内容の変化そのものは検出し、変化時に1度だけ通知する**。再承認を求めない代わりに「変わったこと」の可視性は保つ(#3) |
| 明示的な不承認 | 値に `false` を書くと「確認したうえで承認しない」を表明でき、未承認通知を抑止する |
| ワイルドカード | `trusted_projects` に `"*"` 等の**全プロジェクト一括承認は実装しない**。ピン留めなし承認もプロジェクトパス単位である |
| 承認 UX | フックは非対話(stdin はイベント JSON)のためプロンプトを出せない。`systemMessage` に**貼り付け可能な承認エントリを印字**し、ユーザーがグローバル設定へ手で追加する |
| 信頼ゲートの堅牢性 | `trusted_projects` は**参照より前に**防御的に型検査する。不正は「非承認」へ縮退させ、**例外にしない**(レビュー指摘1) |
| 型不正時のフォールバック先 | ビルトイン `DEFAULTS` ではなく**直下の層の値**へ戻す(レビュー指摘2)。挙動仕様 #5 |
| 通知の配線 | `cfg["_notices"]` を新設し `hook_io.finalize` が一元的に消費する。実装site は 1 箇所(レビュー指摘3) |
| 通知の流量 | 「未承認」は状態ファイルでクールダウン。「ハッシュ不一致」は**常に出す**(セキュリティ事象のため) |
| 値検証との関係 | **直交する別 spec**。値検証(`custom_patterns` の要素・正規表現 compile・走査長上限)は信頼層と無関係に全層へ適用する |
| スコープ外 | 承認用 CLI、部分承認、fail-open 意味論の分離、`.claude/settings.json` 系(config_guard が担当) |

## 設計原則(不変条件)

1. **非承認のプロジェクト設定は解析しない。** ハッシュ計算のためにバイト列は読むが、JSON としてパースしない。使わないデータを解析しないことで、深いネストによる `RecursionError` 等の解析時攻撃面が非承認プロジェクトに対して構造的に消える。
2. **承認は内容に対して行う。** パスに対してではない。ファイルが 1 バイトでも変われば承認は失効する。
3. **無視したことは必ず可視化する。** サイレントな無効化は本 Hooks 集が塞いでいる失敗クラスそのもの(F3 の教訓)。ただし可視化は**継続利用に耐える頻度**でなければならない — 毎ツール呼び出しで複数回出るような通知はユーザーにプラグイン自体を無効化させ、結果としてセキュリティを損なう(#3)。
4. **信頼判定の機構自体が例外を投げてはならない。** ガードを守るための判定が、ガードを落とす経路になってはならない(レビュー指摘1)。
5. **上位層の不正は直下の層へ縮退する。** 層構造の意味は「上位が下位を上書きする」であり、上位が壊れたときの縮退先は最下層ではなく直下の層である(レビュー指摘2)。
6. **グローバル層の挙動は一切変えない。** 本変更はプロジェクト層のみに作用する(#5 のフォールバック修正は、グローバル層の値を**より忠実に保つ**方向の変更である)。

## 挙動仕様

### #1 承認レコードのスキーマと検証

グローバル設定 `$HOME/.claude/claude-hooks.json` にトップレベルキー `trusted_projects` を追加する。`DEFAULTS["trusted_projects"] = {}`。

```jsonc
{
  "trusted_projects": {
    // キー: プロジェクトディレクトリの絶対実パス(realpath 解決済み)

    // 既定: 内容ピン留め承認。値は .claude-hooks.json の
    //       生バイト列の SHA-256("sha256:" 接頭辞付き)
    "/home/USER/work/myrepo": "sha256:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",

    // オプトイン: ピン留めなし承認。内容が変わっても承認は継続する
    "/home/USER/work/my-active-repo": true,

    // 明示的な不承認。未承認通知を抑止する(挙動は「承認しない」で同じ)
    "/home/USER/work/someones-repo": false
  }
}
```

- キーは `os.path.realpath(cwd)` で正規化する。シンボリックリンク経由の別名で承認が二重管理されるのを防ぐ。
- 値のハッシュは**パース後の JSON ではなく生バイト列**に対して取る。整形の違いも含めて内容の同一性を担保するため。
- 接頭辞 `sha256:` はアルゴリズム更新余地のために付ける。
- `trusted_projects` は**グローバル層からのみ**読む。プロジェクト層のこのキーは(そもそもマージされないため)自動的に無効である。

**ピン留めなし承認(`true`)の位置づけ。** 内容ハッシュを問わずそのパスのプロジェクト設定を採用する。設定を頻繁に編集するリポジトリで、編集のたびに再承認を求められる摩擦を避けるための**人間の明示的なオプトイン**である。既定ではなく、#3 の通知が印字する承認エントリにも現れない — 利用者が自分で `true` と書いたときにのみ有効になる。

意味するところを `docs/configuration.md` に明記する: このパスのリポジトリについては、**承認後に `git pull` で `.claude-hooks.json` が差し替わっても、そのまま採用される**。#4 の全権限(deny 緩和・コマンド実行)が、将来そのファイルに書かれる内容に対しても前もって与えられる。信頼の対象がファイルの内容ではなく**リポジトリのメンテナ**になる、と理解して選ぶべき設定である。

ただし承認を継続することと変化を見逃すことは別である。ピン留めなしでも**内容の変化そのものは検出し、1度だけ通知する**(#3)。

**真偽値は厳密に判定する。** `true` / `false` は**JSON の真偽値そのもの**でなければならない。`"true"`(文字列)・`1`・`[]` 等の truthy/falsy な値は承認として扱わず、#1 の検証表に従って無視する。Python の `if value:` ではなく `value is True` / `value is False` で判定する。

**防御的検証(原則4)。** 承認判定は既存の型検証(`config.py:98` 以降)より**前**に走るため、その型検証を当てにできない。参照の直前に以下を行い、いずれかに該当すれば**その参照を「非承認」として扱う**。例外は投げず、`load_config` の外側フォールバックへ到達させない。

| 条件 | 扱い |
|---|---|
| `trusted_projects` が dict でない(`[]`・`null`・`"x"`・数値) | 全プロジェクトが非承認。`_notices` に設定不正を1件記録 |
| エントリのキーが str でない | そのエントリを無視 |
| 値が `True`(真偽値) | **ピン留めなし承認**として採用 |
| 値が `False`(真偽値) | **明示的な不承認**。採用せず、未承認通知も出さない |
| 値が str で `sha256:` 接頭辞かつ 16 進 64 桁 | **内容ピン留め承認**の候補としてハッシュ照合へ |
| 値が str だが接頭辞が無い/未知、または 16 進部の長さが不正 | そのエントリを無視(= 未承認扱い。#3 の「未承認」文面) |
| 値がそれ以外(`"true"` 等の文字列・数値・list・dict・`null`) | そのエントリを無視(= 未承認扱い) |

真偽値の判定は `value is True` / `value is False` で行う(#1 の「厳密に判定する」)。`1` や `"true"` が承認になってはならない。

ハッシュ比較は大文字小文字を区別せず、定数時間比較は不要である(秘密ではなく完全性の照合のため)。

### #2 `load_config` の判定フロー

`_load_config` 内、グローバル層をマージした後・プロジェクト層をマージする前に以下を行う。

1. `Path(cwd or ".") / ".claude-hooks.json"` が存在しなければ何もしない(通知も出さない)。`cwd` が `None` でも `Path(None)` を作らない既存イディオム(`config.py:83`)を踏襲する。
2. **`path.read_bytes()` で生バイト列を読む。** `read_text()` を使わない — 不正 UTF-8 のファイルでもハッシュは計算可能であり、承認/未承認の判定を先に成立させるためである。読めなければ既存のエラー処理(F3 で導入済み)に従い、マージはしない。
3. そのバイト列の SHA-256 を計算する。
4. #1 の検証を通したうえで `trusted_projects[realpath(cwd)]` を引く。**採用する場合はいずれも、手順2で読んだバイト列そのものをパース**してマージする(現行と同一の挙動)。ファイルを再オープンしない(TOCTOU 回避)。パースに失敗した場合は既存のエラー処理に従う。

   | エントリ | マージ | 通知 |
   |---|---|---|
   | ハッシュ一致 | する | なし |
   | ハッシュ不一致 | **しない** | 「変更検知」(警告・クールダウン対象外) |
   | `True`(ピン留めなし)・内容が前回と同じ | する | なし |
   | `True`(ピン留めなし)・**内容が前回から変化** | **する** | 「ピン留めなしで変更を採用」(情報・1回のみ) |
   | `False`(明示的な不承認) | しない | **なし**(意図的に抑止) |
   | エントリ無し / #1 で無視されたエントリ | しない | 「未承認」(情報・クールダウンあり) |

   ピン留めなしの変化検出は #3 の状態ファイルに最後に採用したハッシュを記録して行う。状態ファイルが使えない場合は「変化なし」とみなして通知しない(可視性より、ここでは誤警告の回避を優先する — 採用自体は利用者が既に承認しているため)。
5. マージした場合も、その後の型検証・列挙検証(既存 + #5 の変更)はこれまでどおり全層に対して適用する。

### #3 通知の配線と流量

**配線(実装site は 1 箇所)。** `cfg["_notices"]`(list[str])を新設し、`hook_io.finalize` が `_errors` と同様に一元的に `systemMessage` へ合成する。各フックへの個別実装はしない — それは廃止したはずの列挙の同期漏れを、鍵の表から 9 ファイルの通知実装へ移すだけである(レビュー指摘3)。

`_errors` とは意味を分ける。`_errors` は「設定が壊れている」、`_notices` は「設定を意図的に採用しなかった」である。文面接頭辞も分ける。

**`audit_log` は通知を出さない。** `audit_log` は `async: true` で全イベントに配線された非対話のロギングフックであり(`hooks.json`)、`hook_io.finalize(None, cfg_all)` を呼ぶ(`audit_log.py:22,43`)。ここから通知が出るとユーザー向けメッセージが全ツール呼び出しに付く。`finalize` に `quiet_notices: bool = False` を追加し、`audit_log` の 2 箇所のみ `True` を渡す。

**流量制御。** `audit_log` を除いても `Edit` 1 回で `secrets_guard` + `quality_gate` + `secrets_scan` の 3 回通知されうる。原則3 の後段に従い、「未承認」通知にクールダウンを設ける。

- 状態ファイル: `$HOME/.claude/safe-dev-hooks-state.json`。
  `{"notice_last": {"<realpath>": <epoch秒>}, "unpinned_seen": {"<realpath>": "sha256:..."}}`。
  `unpinned_seen` はピン留めなし承認で最後に採用した内容のハッシュで、変化検出に使う。
- クールダウン既定 3600 秒。`notify` セクションではなくトップレベルの新規キー `notice_cooldown_sec` で調整可能とし、`0` で無効化(毎回通知)。
- **ベストエフォート。** 状態ファイルが読めない・書けない・壊れている場合は**通知する側に倒す**(可視性を優先)。ここで例外を投げてはならない(原則4)。
- 並行するフックが同一ツール呼び出しで二重に通知することは許容する。クールダウンは収束すればよい。
- **「ハッシュ不一致」はクールダウンの対象外**とし、常に通知する。悪意ある `git pull` の兆候でありうるセキュリティ事象であり、情報通知とは扱いを分ける。
- **「ピン留めなしで変更を採用」は変化した回でのみ通知する**(クールダウンではなく `unpinned_seen` の差分で制御)。同じ内容が続く限り黙る。
- **`False`(明示的な不承認)は通知しない。** 利用者が確認したうえで判断を表明したものであり、繰り返し促す理由がない。

**文面。**

未承認:

```
[safe-dev-hooks] このプロジェクトの .claude-hooks.json は未承認のため無視しました。
内容を確認のうえ承認する場合は $HOME/.claude/claude-hooks.json の
"trusted_projects" に次を追加してください:
  "/home/USER/work/myrepo": "sha256:9f86d081..."
承認するとこの設定はガードの deny 判定とコマンド実行に対する権限を持ちます。
```

ハッシュ不一致(変更検知):

```
[safe-dev-hooks] 警告: このプロジェクトの .claude-hooks.json は承認後に変更されています。
安全のため無視しました。差分を確認し、意図した変更であれば
"trusted_projects" のハッシュを次の値へ更新してください:
  "/home/USER/work/myrepo": "sha256:新しい値..."
```

ピン留めなし承認で内容が変化したとき(採用はする):

```
[safe-dev-hooks] このプロジェクトの .claude-hooks.json は前回から変更されていますが、
ピン留めなし承認(true)のため、そのまま採用しました。
内容を確認する場合: git diff -- .claude-hooks.json
内容ごとに承認したい場合は "trusted_projects" の値を次のハッシュへ変えてください:
  "/home/USER/work/my-active-repo": "sha256:新しい値..."
```

- 承認エントリは**フックが計算済みのハッシュをそのまま印字**する。ユーザーに `sha256sum` を手で叩かせない。これにより承認用 CLI を追加せずに実用的な UX が成立する。
- パス・ハッシュはフックが実行時に生成する値であり、リポジトリ内に実ユーザー名が入ることはない(`.claude/rules/no-personal-paths.md` に抵触しない)。状態ファイルもリポジトリ外である。

### #4 承認が意味すること(ドキュメント上の明示)

承認済みプロジェクトの設定は**現行と同一の全権限**を持つ。すなわち承認とは以下を許すことである。

- ガードの deny 判定の緩和(`allow_paths`・`allow`・`trusted_servers`・`categories: "off"` 等)
- コマンド実行(`quality_gate.commands`・`notify.command`)
- コンテナイメージとホストパス bind-mount の指定(`scanners.*`)

鍵ごとの制限を設けないのは意図的である(決定事項参照)。この意味を `docs/configuration.md` と `docs/security-model.md` に明記し、承認は「このリポジトリのメンテナを信頼する」判断と同義であることを利用者に伝える。

### #5 型不正時のフォールバック先を直下の層にする

**これは本 spec 以前から HEAD に存在する実バグの修正である**(レビュー指摘2、現行コードで再現確認済み)。

現行の `config.py:98-101` は、マージ後の値が `DEFAULTS[key]` と型が異なるとき `copy.deepcopy(DEFAULTS[key])` を代入する。縮退先が**最下層**であるため、上位層が壊れた型を送り込むと**中間層(グローバル)の強化値まで消える**。

実測(HEAD):

| | グローバルで設定 | プロジェクトが `{"exfil_guard": 0}` を与えた後 |
|---|---|---|
| `exfil_guard.mode` | `always` | `detect`(ビルトイン既定) |
| `exfil_guard.categories.pii` | `deny` | `ask`(ビルトイン既定) |

対応: マージを層ごとに行い、**各層のマージ直後にその層が持ち込んだ値を検証**する。型不正な値は採用せず、**その層をマージする前の状態**を保つ。これにより:

- グローバル層が壊れた型を持つ → ビルトイン既定へ縮退(従来どおり)
- プロジェクト層が壊れた型を持つ → **グローバルマージ後の状態を保つ**(修正点)

原則5 の実装である。既存の列挙検証(`_ENUM_KEYS`・`_CATEGORY_ACTIONS`)およびリスト要素検証も同じ扱いとする。

本 spec に取り込む理由は、これが層間の信頼意味論そのものだからである。値検証 spec(別途)は層と無関係な値の妥当性を扱うのに対し、本項は「どの層へ戻すか」という層構造の問題である。

**先行出荷を妨げない。** 本項は承認機構と独立に適用でき、単独でも現行バグを閉じる。実装順序として #5 を先に出してもよい。

## 保証すること / しないこと

| | |
|---|---|
| **保証する** | 未承認リポジトリを clone して開いただけでは、プロジェクト設定は deny 判定にもコマンド実行にも一切影響しない |
| **保証する** | **内容ピン留め承認(既定)**では、承認後にプロジェクト設定が変更されれば再承認まで無視され、警告が出る |
| **保証する** | **ピン留めなし承認(`true`)**でも、内容が変化した回に1度通知される(採用は止めないが、変化は見逃さない) |
| **保証する** | プロジェクト層の型不正によってグローバル層の強化値が失われない(#5) |
| **保証する** | `trusted_projects` がどのような値であっても、承認判定が例外でガード全体を落とすことはない(#1) |
| **保証しない** | 承認済みリポジトリが後に敵対的になった場合(内容が変われば #2-4 で捕捉されるが、**変更を確認せず再承認した場合は防げない**) |
| **保証しない** | **ピン留めなし承認(`true`)を選んだプロジェクトについては、差し替えられた設定が採用されること自体は止まらない。** 通知は出るが、その時点で既にマージ済みである。この設定を選ぶことは、将来そのファイルに書かれる内容に対して #4 の全権限を前もって与えることを意味する |
| **保証しない** | ピン留めなし承認の変化検出は状態ファイルに依存する。状態ファイルが失われた/書けない環境では変化通知が出ない(採用は従来どおり行われる) |
| **保証しない** | 承認済みプロジェクトによる deny 緩和・コマンド実行(#4 のとおり承認の定義そのもの) |
| **保証しない** | グローバル設定自体の汚染(定義上の信頼層) |
| **保証しない** | ReDoS・不正な値による堅牢性の問題(**別 spec の値検証で扱う**。承認済み設定でも、善意のユーザーの正規表現の打ち間違いで発生しうる) |
| **保証しない** | 未承認通知のクールダウン中に、同一プロジェクトの通知が抑制されること自体は可視性の低下である(#3 のトレードオフとして受容) |

## 既知の副作用とその決着

### 自リポジトリのドッグフーディングが既定で失効する

本リポジトリの `.claude-hooks.json` は `secrets_scan.custom_patterns` で `real-home-path` 規約を機械的に強制している(`.claude/rules/no-personal-paths.md`)。オプトイン下では**新規クローン・新規コントリビュータ・新規 worktree は未承認状態**となり、この検出が効かない。

**受け入れる。** 根拠:

1. `no-personal-paths.md` は強制レイヤを 2 つ挙げている — `custom_patterns` と **CI のリークチェック**。CI(`.github/workflows/ci.yml`)は本機構と完全に independent な `git grep` であり、最終防衛線は残る。
2. 未承認時は `systemMessage` が出るため、**サイレントな喪失にはならない**(原則3)。

`CONTRIBUTING.md` には**2 つの選択肢**を記載する(レビュー指摘の非 blocking 改善):

- プロジェクト設定を承認する(#3 の印字エントリを貼り付ける)
- **`real-home-path` パターンを各自のグローバル設定に入れる** — グローバル層は常に信頼されるため、承認の有無・worktree の増減と無関係に常時有効になる。コントリビュータにはこちらの方が堅牢である

### worktree・モノレポでの再承認コスト

承認は `realpath(cwd)` 単位である。`git worktree add` で作った作業ツリーは別パスとなり、**同一リポジトリでも改めて承認が必要**になる。モノレポ内のサブディレクトリが独自の `.claude-hooks.json` を持つ場合も同様である。

これは意図した挙動である(便乗承認を構成上不可能にしている)が、worktree を多用する開発では摩擦になる。`docs/configuration.md` に明記し、頻繁に worktree を作る場合はグローバル設定側に寄せることを推奨する。

なお**ピン留めなし承認(`true`)はこの摩擦を軽減しない** — パス単位である点は変わらないため、worktree ごとに `trusted_projects` へエントリが要る。ピン留めなし承認が解消するのは「同じパスで内容が変わったときの再承認」であって、「パスが増えたときの承認」ではない。

### チーム共有設定の UX が変わる

`docs/configuration.md` §4.2 の「チーム用」プリセットはプロジェクト層前提である。オプトイン後はメンバー各自が一度承認する必要がある。プリセットの記述を更新する。

なお `trusted_servers` のようにガードを緩める値は、そもそもプロジェクト層で共有すべきでない旨も併記する。

### 副産物: git 経由の設定持ち込みは現状まったく不可視である

`config_guard` は `ConfigChange` イベントで発火するが、`.claude-hooks.json` が `git clone`/`git pull` で到着しても Claude Code の設定ファイルではないため **ConfigChange は発生しない**。したがって現状、リポジトリ同梱の設定が持ち込まれたことをユーザーが知る経路は存在しない。

本 spec の未承認通知が、この可視化を**設計上自動的に**もたらす。`config_guard` 側の追加対応は不要とする。

## テスト(原則4: 両方向)

**false-negative 方向(バイパス試行):**

- 未承認プロジェクトの `.claude-hooks.json` に、背景で列挙した全シンク(`allow_paths`・`allow`・`trusted_servers`・`categories: "off"`・`protected_branches: []`・`quality_gate.commands`・`notify.command`・`scanners.*`)を置き、いずれも効果を持たないこと。
- 上記の各シンクについて、`bash_guard`・`secrets_guard` をサブプロセス起動し deny が維持されるブラックボックステスト。
- グローバルで強化した値(`extra_deny`・`protected_paths`・`mode: "always"`・`categories.pii: "deny"`)が、未承認プロジェクト設定によって既定値へ戻らないこと。**却下ラウンド1の型すり替え形状**(`{"exfil_guard": 0}`、`"x"`、`[]`、`null`、`true`、`1.5`)を全て含める。
- **同じ型すり替え形状を、承認済みプロジェクトからも試す**(#5 の回帰テスト)。グローバルの強化値が保たれること — ビルトイン既定へ戻らないこと。
- ハッシュ不一致時にマージされないこと(承認後にファイルを 1 バイト変更)。
- `trusted_projects` にワイルドカード・未知の接頭辞・長さ不正のハッシュ・非 str のキーを置いても承認とみなされないこと。
- **truthy な非真偽値が承認にならないこと** — `"true"`(文字列)・`1`・`[]`・`{}`・`"yes"` を値に置いても未承認として扱われること(`value is True` 判定の確認)。
- `False` を置いたプロジェクトがマージされないこと。
- **`trusted_projects` 自体が `[]`・`null`・`"x"`・数値のとき、例外が外へ出ずガード全体が落ちないこと**(#1 の回帰テスト、レビュー指摘1)。グローバルの他の強化値が保たれることも併せて確認する。
- プロジェクト層に `trusted_projects` を置いても自己承認できないこと。
- 不正 UTF-8 のプロジェクト設定でも、ハッシュ計算と未承認判定が成立すること(`read_bytes()` の確認)。

**false-positive 方向(正当操作の維持):**

- 承認済み(ハッシュ一致)なら、プロジェクト設定が**現行と完全に同一に**適用されること(本リポジトリ自身の `real-home-path` パターンを含む)。
- グローバル設定のみの環境で、挙動が本変更前と一致すること。
- プロジェクト設定が存在しない場合、通知が出ないこと。
- `cwd` が `None`・存在しないパス・シンボリックリンク経由のとき、例外を出さず妥当に振る舞うこと。
- realpath 正規化により、同一リポジトリへの別名パスで承認が二重に必要にならないこと。
- **`audit_log` が未承認通知を出さないこと**(`quiet_notices=True` の確認、#3)。
- **クールダウンが機能すること** — 連続呼び出しで 2 回目以降が抑制され、クールダウン経過後に再度出ること。状態ファイルが壊れている/書けない場合は通知される側に倒れること。
- **ハッシュ不一致通知はクールダウンされないこと**。
- **ピン留めなし承認(`true`)で、内容を変更してもマージされ続けること**(本機能の主目的)。
- **ピン留めなし承認で、内容が変化した回にのみ通知が出ること** — 変更直後は通知、同じ内容での再実行は無通知、再度変更でまた通知。
- **ピン留めなし承認で状態ファイルが使えないとき、変化通知は出ないがマージは継続すること**。
- **`False` のプロジェクトで未承認通知が出ないこと**(通知抑止の確認)。

## ドキュメント・リリース

- `docs/configuration.md` — 信頼層の節を新設(グローバル=信頼 / プロジェクト=要承認)、`trusted_projects` スキーマ(ハッシュ / `true` / `false` の3形式)、`notice_cooldown_sec`、承認手順、worktree の注意、§4.2 チーム用プリセットの更新。**ピン留めなし承認は独立した小節を立て、「将来そのファイルに書かれる内容へ前もって全権限を与える」という意味を明記する**(#1)。既定はハッシュ固定であり、通知が印字するエントリも常にハッシュ形式であることを併記する。
- `docs/security-model.md` §2 — 「設定ファイルからの deny 層解除不可」の保証を、実装が満たす内容へ書き改める。**実装が保証しないことを書かない**(却下ラウンド2でドキュメントが実装を上回った失敗の再発防止)。#5 のフォールバック意味論も明記する。
- `CONTRIBUTING.md` — 開発環境セットアップに承認手順を追加。グローバル設定に寄せる選択肢も併記する。
- `README.md` / `README.ja.md` — プロジェクト設定の扱いが変わる旨。最小例がプロジェクト層前提なら修正。
- `CHANGELOG.md` — **破壊的変更**として記載。既存利用者のプロジェクト設定は承認まで無効になる。#5 は独立した修正項目として記載する。
