# quality_gate の自動検出を承認制にする(0.8.0) 設計

## 背景 — 何が問題か

`hooks/post_tool_use/quality_gate.py` の `AUTO_DETECT` は既定で有効
(`DEFAULTS["quality_gate"] = {"enabled": True, "mode": "block", "commands": {}}`)であり、
`commands` が空のとき次を実行する。

```python
AUTO_DETECT = [
    ("*.py",                        "ruff",    ("pyproject.toml", "ruff.toml", ".ruff.toml"), "ruff check {file}"),
    ("*.rs",                        "rustfmt", ("Cargo.toml",),                               "rustfmt --check {file}"),
    ("*.js|*.jsx|*.ts|*.tsx",       "npx",     ("package.json",),                             "npx --no-install eslint {file}"),
]
```

実行はマーカーファイルが**プロジェクトルート**にあるときに起こり、0.7.1 以降は実行ディレクトリも
プロジェクトルートである(D4)。

**問題**: eslint は `eslint.config.js` を読む。これは**リポジトリが同梱する JavaScript であり、
評価される**。つまり clone しただけの未承認リポジトリで `.js` を 1 ファイル編集すると、
承認も通知もないままリポジトリ由来のコードが実行され得る。`ruff`(TOML)・`rustfmt`(TOML)は
宣言的な設定しか読まないため危険度は低いが、同じ経路である。

0.7.0 の信頼ゲートは**利用者が書いた `quality_gate.commands`** を承認制にしたが、`AUTO_DETECT` は
組み込みのためゲートの外側にある。さらに 0.7.1 でマーカー探索がルート基準になった結果、
サブディレクトリ作業中にも発火するようになり、**露出はむしろ広がった**(修正前はマーカーが
見つからず自動検出がスキップされていた)。

### 実測(利用 3 プロジェクト、17 日分・25,962 イベント)

`npx` と `node` は実在する。`eslint` 自体は未導入なので `--no-install` が現状は止めるが、
`node_modules` を同梱したリポジトリでは通る。これは環境依存の偶然であって、設計上の防御ではない。

## 決定事項

| # | 決定 | 理由 |
|---|---|---|
| D1 | **`AUTO_DETECT` は「承認済みプロジェクト」でのみ実行する** | 脅威(リポジトリ由来の設定が実行される)と対処範囲が一致する |
| D2 | 「承認済み」= **`trusted_projects` にそのプロジェクトのエントリがある**こと。プロジェクト設定ファイル `.claude-hooks.json` の有無は問わない | 悪意あるリポジトリは `.claude-hooks.json` を同梱しなければよいので、「プロジェクト設定が採用されたか」で判定しても脅威を捉えられない。判定すべきは「利用者がこのディレクトリを信頼したか」である |
| D3 | 承認値の種別(`"sha256:…"` ピン留め / `true` ピン留めなし)は**問わない**。`false`(明示的な不承認)と未登録は「未承認」 | ピン留めは `.claude-hooks.json` の内容に対する承認であり、ディレクトリを信頼したという事実は両者に共通する |
| D4 | スキップしたときは**通知する**(クールダウン付き) | 0.7.0 の「採用しなかったものは必ず通知する」原則と一貫させる。黙って lint が走らなくなると、利用者は「動いている」と誤解する |
| D5 | 利用者が明示した `quality_gate.commands` の扱いは**変更しない** | それは 0.7.0 の信頼ゲートで既に承認制になっている(未承認ならプロジェクト設定自体が読まれない)。グローバル設定に書いた `commands` は利用者自身の意思なのでそのまま実行する |
| D6 | バージョンは **0.8.0** | 既定で動いていた機能が未承認プロジェクトで止まる、利用者から見える挙動変更のため。0.7.0(破壊的変更)と同じ扱い |

### D2 の含意(利用者への影響)

未承認の普通のリポジトリでは自動 lint が走らなくなる。これは**意図した挙動**である。
自動 lint はガードではなく利便機能であり、走らないこと自体は危険ではない。一方で
「未承認リポジトリのコードを実行しない」は守るべき性質である。承認は通知に印字される
エントリを貼るだけで済むので、回復コストは低い。

## 挙動仕様

### #1 判定の所在

判定は `quality_gate` の呼び出し側ではなく**ライブラリ側**に置く。`config.load_config` が
返す設定に、そのプロジェクトが承認済みかどうかを載せる。

- `cfg["_project_trusted"]` を追加する(bool)。`_load_config` が `trusted_projects` を
  参照して決める。プロジェクトルートが解決できない場合(`project_root` が `None`)は `False`。
- 既存の `cfg["_errors"]` / `cfg["_notices"]` と同じく、**必ず存在する**キーとする
  (`load_config` の例外フォールバック経路でも `False` を入れる)。
- `trust` 側に判定関数を置く: `trust.is_trusted(root, trusted_projects) -> bool`。
  `classify_entry` の分類(`pinned` / `unpinned` / `denied` / `ignored`)を再利用し、
  `pinned` と `unpinned` を「承認済み」とする。`denied`・`ignored`・未登録は未承認。

**なぜ call site に置かないか**: 呼び出し側に判断を置くと、将来別のフックが同じ判断を
必要としたときに実装が分岐し、1 箇所の直し漏れが無言のセキュリティ低下になる。0.7.1 の
`project_root` と同じ方針を採る。

### #2 `AUTO_DETECT` の分岐

`resolve_commands(file_path, cfg, cwd)` に承認状態を渡す。利用者が明示した `commands` に
一致した場合は**従来どおり**返す(D5)。一致せず `AUTO_DETECT` へ落ちる場合のみ、
未承認なら空リストを返す。

### #3 通知

未承認のためスキップしたとき、`cfg["_notices"]` に通知を足す — ではなく、**`quality_gate`
自身が出す**。理由: `_notices` は `load_config` の結果に付随するもので、全フックが共有する。
自動検出のスキップは `quality_gate` 固有の事情であり、他フックの出力に載せるのは筋が違う。

- 文面は `trust.py` に置く(利用者向け通知文の集約という既存の設計を維持)。
- クールダウンは既存の状態ファイル機構を再利用し、新しいセクション `autodetect_last` を使う。
  キーはプロジェクトルートの realpath。既定 `notice_cooldown_sec`(3600 秒)。
- 状態ファイルが使えない場合は**毎回通知する**(可視性優先。既存の `_untrusted`・
  `notify_skipped` と同じ側に倒す)。
- 通知に含めるもの: 承認されていないため自動検出を実行しなかったこと、対象プロジェクトの
  realpath、承認する場合に貼るエントリ(`trust` の既存の通知と同じ形式)。
- **実行するコマンドの中身は通知に載せない** — 未承認リポジトリ由来の文字列を利用者の
  端末へそのまま出すのは避ける。

### #4 変えないもの

- `secrets_guard`・`bash_guard`・`exfil_guard` などガード層の判定は一切変更しない。
- `quality_gate.enabled: false` の扱いは従来どおり(自動検出も走らない)。
- `mode`(`block`/`warn`)の意味は変わらない。
- グローバル設定に書いた `commands` は承認の有無に関わらず実行する(D5)。

## 保証すること / しないこと

**保証する**: 未承認プロジェクトでは、`AUTO_DETECT` が起動する外部コマンド
(`ruff` / `rustfmt` / `npx eslint`)は実行されない。したがってそれらがリポジトリ同梱の
設定ファイル(`eslint.config.js` を含む)を読み込むこともない。

**保証しない**:
- 承認済みプロジェクトでの実行は従来どおりである。承認とは「このリポジトリのメンテナを
  信頼する」という表明であり、`eslint.config.js` の評価もその信頼の範囲に入る。
  これは `docs/configuration.md` の信頼層の説明と同じ性質である。
- 利用者がグローバル設定の `commands` に書いたコマンドは、承認の有無に関わらず実行される。
- `quality_gate` 以外の経路(利用者自身が Bash で lint を叩く等)は対象外。

## 副作用(ドッグフーディング)

このリポジトリ自身は `trusted_projects` に登録済みなので、開発体験は変わらない。
未登録のリポジトリで作業すると自動 lint が止まり、通知が出る。

## テスト

両方向で書く。

- 承認済み(`sha256:` ピン留め / `true` の両方)→ `AUTO_DETECT` が従来どおり解決される
- 未承認(未登録 / `false`)→ `AUTO_DETECT` は空リスト、外部コマンドは起動しない
  (`subprocess.run` をスパイして**呼ばれないこと**を固定する)
- 未承認でも利用者が明示した `commands` に一致すれば実行される(D5 の回帰)
- `trusted_projects` が不正な型 → 未承認として扱い、例外を出さない
- `project_root` が `None` → 未承認扱い
- 通知: 初回は出る、クールダウン内の 2 回目は出ない、`notice_cooldown_sec: 0` なら毎回出る、
  状態ファイルが使えないときは毎回出る、通知文の全文一致
- 通知にリポジトリ由来のコマンド文字列が含まれないこと
- `cfg["_project_trusted"]` が例外フォールバック経路でも必ず存在すること
- 黒箱: 未承認プロジェクトで `.js` を編集するイベントを実フックに流し、外部コマンドが
  起動しないことと通知が出ることを確認する
